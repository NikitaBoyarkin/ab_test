## 1. Executive Summary

A/B Testing Methodology Toolkit — эмпирический, калибровочный набор методов A/B-тестирования, реализованных по первоисточникам и валидированных симуляцией. Каждый модуль поставляется с A/A-проверкой нуля и калибровкой power/coverage: числа проверены, а не приняты на веру. Проект решает проблему доверия к статистическим методам — вместо асимптотических обещаний каждый метод прогоняется end-to-end на синтетических данных, и отчёт показывает эмпирические Type I error и power. Ожидаемый эффект: методологически корректный, проверяемый инструментарий для практикующих аналитиков и сильный портфельный кейс.

## 2. Problem Statement

### Текущая ситуация
Методы A/B-тестирования (sequential testing, CUPED, ratio-метрики, HTE) часто применяются «как написано в статье», без проверки того, что метод действительно контролирует Type I error и имеет заявленную мощность. Классические ловушки:
- **Наивное подглядывание** (peeking) инфлейтит Type I error — ранняя остановка без alpha-spending ломает выводы.
- **Ratio-метрики** (CTR, RPC) с наивным per-unit t-тестом дают смещённую стандартную ошибку.
- **Множественные сравнения** без коррекции (Bonferroni/BH) дают ложные срабатывания.
- **SRM** (Sample Ratio Mismatch) не проверяется до основного теста — баги бакетирования ломают всё downstream.

### Влияние на пользователя
- **Кто затронут:** практикующие аналитики и data scientists, принимающие продуктовые решения по результатам экспериментов.
- **Как затронут:** ложные срабатывания (запуск неработающих фич), пропущенные эффекты (низкая мощность), спорные выводы при остановке эксперимента.
- **Серьёзность:** High — статистическая ошибка напрямую конвертируется в продуктовые и бизнес-решения.

### Бизнес-влияние
- **Стоимость проблемы:** запуск неэффективных фич, потерянный трафик экспериментов, неверная интерпретация результатов.
- **Стратегическая важность:** методологическая грамотность в A/B-тестировании — ключевая компетенция data-аналитика; проект демонстрирует глубину понимания, а не только умение вызывать `scipy.stats`.

### Почему решать сейчас
Проект уже реализован (15 модулей, тесты, CI) и используется как портфельный кейс. PRD фиксирует текущее состояние как контракт и задаёт roadmap развития: новые методы, UX/документация, интеграции.

## 3. Goals & Success Metrics

### Goal 1: Калибровка методов (корректность)
- **Описание:** каждый метод контролирует Type I error ≈ α и имеет заявленную power/coverage в допусках.
- **Метрика:** доля проходящих калибровочных тестов в `tests/`.
- **Baseline:** 100% (текущий набор тестов зелёный).
- **Target:** 100% при добавлении новых модулей (каждый новый метод обязан пройти A/A-проверку).
- **Срок:** непрерывно (CI на каждый push).
- **Метод измерения:** `uv run pytest` + CI (`.github/workflows/ci.yml`).

### Goal 2: Покрытие методологии
- **Описание:** покрытие канонической литературы по A/B-тестированию.
- **Метрика:** количество модулей-методов.
- **Baseline:** 15 модулей.
- **Target:** 20+ модулей (stratified, ML-based CUPED, variance reduction для ratio, power-анализ для sequential).
- **Срок:** 3–6 месяцев.
- **Метод измерения:** инвентарь `scripts/`.

### Goal 3: Использование в работе
- **Описание:** модули применяются в реальных задачах (работа, портфельные кейсы).
- **Метрика:** количество кейсов применения вне самого репозитория.
- **Baseline:** 0 внешних кейсов.
- **Target:** 2+ кейса (например, разбор реального эксперимента с SRM + CUPED + delta-method).
- **Срок:** 6 месяцев.
- **Метод измерения:** кейс-заметки в vault / портфолио.

## 4. User Stories

### Story 1: Проверка SRM до основного теста
**As a** практикующий аналитик, **I want to** проверить Sample Ratio Mismatch перед любым downstream-тестом, **So that I can** поймать баги бакетирования/трафика до того, как они испортят выводы.

**Acceptance Criteria:**
- [ ] `scripts/srm_test.py` принимает counts A/B и возвращает χ²-статистику, p-value и вердикт.
- [ ] При сбалансированном сплите (50/50) тест не отклоняет нуль (Type I ≈ α).
- [ ] При смещённом сплите (например, 55/45) тест отклоняет нуль с высокой мощностью.
- [ ] Известные-ответы фикстуры (SRM splits) проходят в `tests/test_srm.py`.

**Dependencies:** None

### Story 2: Always-valid p-value для ранней остановки
**As a** data scientist, **I want to** получать always-valid p-value (mSPRT), **So that I can** подглядывать и останавливаться в любой момент без инфляции Type I error.

**Acceptance Criteria:**
- [ ] `scripts/msprt_always_valid.py` выдаёт p-value, валидный при произвольном времени остановки.
- [ ] Калибровка показывает: наивное подглядывание инфлейтит Type I, mSPRT — контролирует.
- [ ] Модуль работает для ratio-метрик через `scripts/sequential_ratio.py`.

**Dependencies:** REQ-005

### Story 3: Калибровочное доказательство для портфолио
**As a** ревьюер портфолио, **I want to** видеть эмпирическую калибровку каждого метода, **So that I can** доверять результатам, а не асимптотическим обещаниям.

**Acceptance Criteria:**
- [ ] Каждый модуль имеет A/A-проверку нуля и power/coverage-калибровку.
- [ ] `scripts/run_full_pipeline.py` генерирует `outputs/report.md` с числами.
- [ ] README документирует философию «числа проверены, не приняты на веру».

**Dependencies:** REQ-013

## 5. Functional Requirements

### Must Have (P0) — существующее ядро

#### REQ-001: SRM-проверка (χ²)
**Описание:** детекция Sample Ratio Mismatch до любых downstream-тестов.

**Acceptance Criteria:**
- [ ] Принимает counts по вариантам, возвращает χ², p-value, вердикт.
- [ ] Type I error ≈ α на сбалансированном сплите (в допуске теста).
- [ ] Мощность высокая на смещённом сплите (55/45).
- [ ] Известные-ответы фикстуры проходят.

**Dependencies:** None

#### REQ-002: Fixed-horizon sizing & power
**Описание:** расчёт n/arm для пропорций и средних.

**Acceptance Criteria:**
- [ ] Формулы для пропорций и средних (двухвыборочные).
- [ ] Эмпирическая power на симуляции совпадает с расчётной в допуске.
- [ ] Обработка edge case: нулевая дисперсия, одинаковые группы.

**Dependencies:** None

#### REQ-003: Ratio-метрики через delta-method
**Описание:** корректная SE для `ΣY/ΣX` (CTR, RPC).

**Acceptance Criteria:**
- [ ] SE по delta-method точна (coverage ≈ 95%).
- [ ] Наивный per-unit t-тест показан как смещённый (демо).
- [ ] Работает для CTR и RPC.

**Dependencies:** None

#### REQ-004: CUPED — снижение дисперсии
**Описание:** использование pre-period данных для сокращения SE.

**Acceptance Criteria:**
- [ ] SE сокращается примерно на `corr(X,Y)²`.
- [ ] Type I error сохраняется ≈ α после применения.
- [ ] Работает для средних и ratio-метрик.

**Dependencies:** None

#### REQ-005: Sequential testing (alpha-spending + mSPRT)
**Описание:** контроль Type I при ранней остановке.

**Acceptance Criteria:**
- [ ] Pocock/OBF границы контролируют Type I при подглядывании.
- [ ] mSPRT даёт always-valid p-value.
- [ ] Калибровка показывает инфляцию Type I у наивного peeking.

**Dependencies:** None

#### REQ-006: Байесовский A/B
**Описание:** аналитические сопряжённые апостериорные (Beta-Binomial, Normal-Normal).

**Acceptance Criteria:**
- [ ] P(B>A), expected loss, ROPE вычисляются корректно.
- [ ] Сходится с частотным результатом на больших выборках (демо).
- [ ] Известные-ответы фикстуры проходят.

**Dependencies:** None

#### REQ-007: Bootstrap CI
**Описание:** percentile и BCa доверительные интервалы.

**Acceptance Criteria:**
- [ ] Coverage ≈ 95% для percentile и BCa.
- [ ] Работает для скошенных метрик и медиан/квантилей.
- [ ] Детерминированность при фиксированном seed.

**Dependencies:** None

#### REQ-008: HTE по сегментам
**Описание:** interaction-модель для гетерогенных эффектов.

**Acceptance Criteria:**
- [ ] Обнаруживает Simpson-парадокс-подобную отмену эффекта.
- [ ] Возвращает ATE по сегментам с SE.
- [ ] Известные-ответы фикстуры (segment uplifts) проходят.

**Dependencies:** None

#### REQ-009: Коррекция множественных сравнений
**Описание:** Bonferroni (FWER) vs Benjamini-Hochberg (FDR).

**Acceptance Criteria:**
- [ ] Bonferroni контролирует FWER.
- [ ] BH контролирует FDR.
- [ ] Демо показывает разницу на синтетике.

**Dependencies:** None

#### REQ-010: Novelty / Primacy
**Описание:** treat×day interaction для временных эффектов.

**Acceptance Criteria:**
- [ ] Детектирует novelty decay и primacy growth.
- [ ] Возвращает оценку эффекта по дням.
- [ ] Работает на синтетических данных с известным эффектом.

**Dependencies:** None

#### REQ-011: Switchback & cluster designs
**Описание:** cluster-robust SE, carryover bias.

**Acceptance Criteria:**
- [ ] Cluster-robust SE корректна (coverage ≈ 95%).
- [ ] Наивная SE показана как over-/under-rejecting.
- [ ] Carryover bias детектируется.

**Dependencies:** None

#### REQ-012: Generic test simulator
**Описание:** калибровка любого DGP + теста.

**Acceptance Criteria:**
- [ ] Принимает произвольный DGP и тест.
- [ ] Возвращает эмпирический Type I и power-кривую.
- [ ] Детерминированность при фиксированном seed.

**Dependencies:** None

#### REQ-013: End-to-end pipeline
**Описание:** реалистичный флоу на синтетике: SRM → CUPED → delta-method CTR → HTE с BH → novelty → отчёт.

**Acceptance Criteria:**
- [ ] `scripts/run_full_pipeline.py` генерирует `outputs/report.md`.
- [ ] Каждый шаг использует соответствующий модуль.
- [ ] Отчёт содержит числа, а не только вердикты.

**Dependencies:** REQ-001, REQ-003, REQ-004, REQ-008, REQ-009, REQ-010

## 6. Non-Functional Requirements

### Performance
- Полный калибровочный набор (`uv run pytest`): < 10 мин.
- Демо одного модуля: < 30 с.
- End-to-end pipeline: < 2 мин.

### Reliability
- Детерминированность: фиксированные seed'ы, воспроизводимые результаты.
- CI: ruff + pytest зелёные на каждый push.
- Error rate: 0% — тесты не флакают (проверено калибровкой).

### Compatibility
- Python >= 3.11.
- Менеджер: uv.
- Зависимости: numpy, pandas, scipy, statsmodels, plotnine.

### Code Quality
- Ruff: `select = ["E", "F", "I", "UP", "B"]`, `ignore = ["E501", "UP009"]`.
- Покрытие тестами: каждый модуль имеет калибровочный тест.

## 7. Technical Considerations

### Архитектура
```
scripts/            метод-модули (один топик каждый) + end-to-end pipeline
tests/              калибровочный набор (Type I, power, coverage, known-answer)
plots/  outputs/    генерируемые артефакты (gitignored)
.github/workflows/  CI: ruff + pytest
```

### Технологический стек
- **Язык:** Python >= 3.11
- **Наука:** numpy, pandas, scipy, statsmodels
- **Визуализация:** plotnine
- **Инструменты:** uv, pytest, ruff

### Внешние зависимости
1. **Первоисточники:** Deng et al. (2013, 2018), Johari et al. (2015), Lan & DeMets (1983), Benjamini & Hochberg (1995), Efron (1987) — методологическая база, не runtime-зависимости.

### Тестирование
- Unit: калибровочные тесты на каждый метод.
- Known-answer: фикстуры (SRM splits, segment uplifts).
- CI: ruff + pytest на push.
